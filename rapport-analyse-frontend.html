Vue d'Ensemble du Projet

Il s'agit d'une application Angular enterprise dédiée à la gestion des règles métier douanières et des processus BPMN. Elle s'intègre à un backend Spring Boot via une API REST, utilise Keycloak pour l'authentification, et propose une nouvelle fonctionnalité de génération de règles par langage naturel (NLP).

Problèmes de Sécurité

🚨

CRITIQUE — Secret Keycloak exposé dans le code source

Le client secret Keycloak est codé en dur dans keycloak.service.ts (ligne 103) : '63728T3LdLgCzHfBoQlbcmuSoADXQ8nP'. Ce secret est visible dans le navigateur via les DevTools, dans le bundle JS, et dans l'historique Git. Toute personne ayant accès au dépôt peut l'extraire et usurper l'identité de l'application.

🚨

CRITIQUE — URLs de production codées en dur

Toutes les URLs backend (localhost:8081, localhost:8080) sont écrites directement dans le code source. Il n'existe aucun fichier environment.ts configuré pour distinguer les environnements dev/prod. Le déploiement en production nécessitera de modifier manuellement des dizaines de fichiers.

🚨

CRITIQUE — Authentification directe avec identifiants utilisateur

La méthode loginWithCredentials(username, password) dans KeycloakService envoie les identifiants en clair via une requête directe au serveur Keycloak. Cette approche contourne le flux OAuth2 standard (Authorization Code Flow) et présente des risques si la connexion n'est pas HTTPS.

⚠️

MOYEN — Pas de validation côté client sur les entrées utilisateur

Les formulaires de création/édition de règles n'ont pas de validation robuste sur les champs. Des injections de code via les champs libres ne sont pas vérifiées avant envoi au serveur.

⚠️

MOYEN — Vérification d'authentification synchrone

isLoggedIn() retourne une Promise<boolean> mais est utilisée de manière synchrone dans certains templates. Si la vérification échoue silencieusement, l'utilisateur peut accéder à des routes protégées.

Plan de Correction Sécurité

Immédiat — Supprimer le secret du code
Retirer clientSecret de keycloak.service.ts. Configurer Keycloak pour utiliser PKCE (Authorization Code Flow sans secret). Ne jamais réutiliser ce secret.
Immédiat — Créer les fichiers environment
Créer src/environments/environment.ts et environment.prod.ts avec les URLs des APIs. Mettre à jour tous les services pour utiliser ces constantes.
Court terme — Intercepteur d'erreurs global
Ajouter un HttpInterceptor pour gérer les 401 (refresh token ou redirection login) et les 500 (message d'erreur utilisateur).
Court terme — Validation des formulaires
Implémenter Angular Reactive Forms avec des validateurs sur tous les champs. Afficher les erreurs de validation champ par champ.

// nlp.model.ts
interface NlpRegleDto {
  code: string;
  nom: string;
  action: string;
  categorieType: string;
  conditions: Condition[];
}

interface NlpConversionResult {
  regle: NlpRegleDto;       // Règle structurée générée
  drl: string;              // Code Drools Rule Language
  confidence: number;       // Score de confiance (0.0 → 1.0)
  ambiguites: string[];     // Liste des ambiguïtés détectées
  phraseOriginale: string;  // La phrase saisie par l'utilisateur
}

interface NlpConversionRequest {
  phrase: string;           // Phrase en langage naturel
}

Recommandations & Plan d'Action

Priorité 1 — Actions Immédiates (Sécurité)

🔴

1. Supprimer le client secret Keycloak du code

Utiliser le flux OAuth2 PKCE (sans secret client) ou déplacer toute communication sensible Keycloak vers le backend. Régénérer le secret actuel car il est compromis dès lors qu'il est dans l'historique Git.

🔴

2. Créer les fichiers d'environnement Angular

Créer src/environments/environment.ts (dev) et environment.prod.ts (production) avec toutes les URLs. Remplacer tous les http://localhost:8081 par environment.apiUrl.

Priorité 2 — Court Terme (1-2 semaines)

  • 🟡
    Ajouter un intercepteur d'erreurs HTTP global
    Gérer 401 (refresh token), 403 (accès refusé), 500 (erreur serveur) avec des messages utilisateur clairs
  • 🟡
    Déplacer les routes dans app.routes.ts
    Et activer le lazy loading pour améliorer les performances initiales
  • 🟡
    Créer un service de notifications toast centralisé
    Éliminer la duplication du code toast dans RegleMetierComponent et NlpInputComponent
  • 🟡
    Améliorer NlpRegleService
    Ajouter catchError, timeout(30000), et retry(2) via les opérateurs RxJS
  • 🟡
    Valider les formulaires avec Angular Reactive Forms
    Remplacer les validations manuelles par des Validators Angular

Priorité 3 — Moyen Terme (1-2 mois)

  • 🔵

  • 🔵

  • 🔵

Priorité 4 — Long Terme (3-6 mois)

  • ⚪ Mettre en place NgRx ou un store basé sur les Signals pour la gestion d'état

Exemple de Correction — NlpRegleService

// AVANT (problématique)
convertir(phrase: string): Observable<NlpConversionResult> {
  return this.http.post<NlpConversionResult>(
    'http://localhost:8081/api/nlp/convertir', { phrase }
  );
}

// APRÈS (recommandé)
convertir(phrase: string): Observable<NlpConversionResult> {
  return this.http.post<NlpConversionResult>(
    `${environment.apiUrl}/nlp/convertir`, { phrase }
  ).pipe(
    timeout(30000),
    retry(2),
    catchError(err => throwError(() => new Error(
      err.status === 0
        ? 'Serveur inaccessible'
        : `Erreur ${err.status} : ${err.error?.message ?? 'Inconnue'}`
    )))
  );
}

Conclusion

L'application frontend Angular analysée est un projet enterprise bien structuré, avec une architecture moderne (composants standalone, TypeScript strict, intégration Keycloak/Camunda/BPMN) et une interface utilisateur soignée. La nouvelle fonctionnalité NLP est particulièrement bien conçue côté UX.

Cependant, trois problèmes critiques de sécurité doivent être résolus avant tout déploiement en production, notamment l'exposition du secret Keycloak et l'absence de configuration d'environnement. L'absence totale de tests unitaires représente également un risque important pour la maintenabilité future.
